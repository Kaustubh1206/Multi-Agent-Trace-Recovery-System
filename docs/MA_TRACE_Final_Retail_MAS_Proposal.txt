REVISED RESEARCH AND IMPLEMENTATION PROPOSAL
MA-TRACE
Multi-Agent Tracking, Recovery, Attribution, and Consistent Evaluation
An evidence-driven failure diagnosis, containment, and recovery framework for retail multi-agent workflows
Project status: proposed system and experimental plan; no performance gains or novel results are claimed before evaluation.
Abstract
LLM-based multi-agent systems can fail when one agent passes an incorrect order identifier, misreads a policy, skips customer confirmation, or triggers an unsafe tool action. A later agent may produce the visible error even when the original mistake occurred in an earlier handoff. MA-TRACE proposes an independent reliability layer for a custom LangGraph retail multi-agent system. It records observable actions and state changes, links dependent decisions across agents, identifies likely failure causes, holds risky downstream actions, applies bounded recovery, and verifies the resulting database state before releasing the workflow. The initial application and evaluation will use the Retail domain of the τ-bench benchmark, complemented by deterministic fault-injection cases and independent expected-state checks. The intended contribution is not a new graph model by itself but a measurable, multi-agent-aware policy for dependency-based containment and verified selective recovery.
1  Problem statement
Design, implement, and experimentally evaluate MA-TRACE: a fault-attribution and safe-recovery layer for a retail LLM multi-agent system. When a task fails, MA-TRACE should identify which agent and step most likely introduced the fault, determine which downstream decisions are affected, prevent unsafe state changes, and repair only the necessary work where possible. Its outcome must be checked against task requirements and the actual simulated environment rather than accepted solely because an LLM says the answer looks correct.

3  Retail application and benchmark
The application is an original LangGraph multi-agent workflow for customer support; it is not presented as an existing multi-agent implementation supplied by AgentTether. Its benchmark foundation is τ-bench Retail, which provides customer requests, a retail policy, tool APIs, a simulated order/customer database, and externally checkable outcomes. AgentTether evaluated 114 retail tasks, with 26 initially failed under its particular model/run setup; our initially failed set will be measured independently and must not be assumed to match 26.

3.2  Explainable retail workflow

Representative tasks include pending-order cancellation, modifying a pending order’s address/payment/item variant, returning or exchanging delivered items, changing a profile address, and retrieving information. The τ-bench Retail policy requires authentication and explicit user confirmation before consequential writes; some modification/exchange tools can be called only once. All actions in this project use simulated tools and databases, never actual customer payments.
4  Overall MA-TRACE system architecture
MA-TRACE runs beside the retail agents, rather than acting as a competing customer-facing agent. It receives execution evidence through structured LangGraph callbacks/middleware and checks state-changing actions at controlled boundaries.

4.1  Core components, in plain language
Plain-language component
Purpose (technical term)
Step record
One observed decision, tool action, feedback, and state delta; analogous to an AgentTether Transition Unit (TU).
Dependency map
Connects earlier outputs to later actions across agents; a multi-agent extension inspired by the Critical Transition Graph (CTG).
Failure checker
Combines deterministic rules, run-local outlier scoring (optional Isolation Forest), and evidence-ranked candidate causes.
Impact and safety gate
Determines which dependent artifacts are suspect and blocks unsafe proposed writes until verified.
Repair controller
Selects minimal safe action: correct an input, refresh a tool result, rerun affected nodes, full retry, or escalate.
Independent verifier
Checks expected tool calls and the simulated database state; repair success is never LLM judgment alone.
An HGT (Heterogeneous Graph Transformer) is the paper’s learned normal-behavior detector—not another name for the dependency graph. Because it requires substantial normal-trace training data, the first working prototype will use deterministic checks and a small run-local detector; HGT becomes an optional controlled enhancement, not a hidden prerequisite.
5  Method: from failure to safe recovery
5.1  Track observable evidence
Every agent and tool event will receive a run_id, event_id, agent_id, step_id, time, tool name and arguments, source agent, destination agent, message or handoff ID, consumed artifact versions, produced artifacts, state reads/writes, status, checkpoint ID, and effect class (read versus state change). No access to hidden LLM chain-of-thought is assumed; “reasoning” refers only to observable messages and decisions.
5.2  Build a cross-agent dependency map
Construct edges only when supportable: a data edge when a later agent consumes an earlier result; a handoff/control edge when one agent delegates; a state edge from versioned reads/writes; and a tool-effect edge for committed external changes. Mere time order is not treated as proof of causation. Unknown dependencies are conservatively flagged.
5.3  Detect and attribute
Start with explicit checks for wrong order/customer IDs, missing authentication or consent, invalid policy conditions, stale versions, wrong tool arguments, duplicated writes, and unfinished required actions. Rank candidate agent+step pairs using violated checks and upstream dependencies. Run-local anomaly scoring may improve ranking; the diagnostic LLM can explain a candidate only when it cites event IDs. Distinguish the injection point, the earliest observable error, and the decisive cause: these may not be identical.
5.4  Contain and choose a recovery
Before a consequential write, the gate checks authorization, confirmation, policy preconditions, artifact validity, state version, and an operation ledger. If the required evidence is invalid or uncertain, hold the action; select correction, refresh, safe selective replay, or escalation. Keep unaffected observations and prevent a committed refund/cancellation from running twice. A checkpoint cannot reverse a previously committed side effect.
5.5  Replay and verify
If safe, fork from the last valid checkpoint, replace the faulty input or tool result, rerun only affected descendants, then check the proposed outcome with the benchmark oracle and deterministic state assertions. Commit a simulated write only once using an idempotency key and effect ledger. On rejection, retry within a fixed cap or escalate; record the result in repair memory.
6  Worked example: failure across agents
Event
What happens
1. Customer / Supervisor
User asks to cancel ORDER-A. Supervisor mistakenly passes ORDER-B downstream.
2. Order / Policy
Order Agent retrieves ORDER-B; Policy Agent approves cancellation on its status.
3. Safety check
Action Agent is about to cancel ORDER-B. MA-TRACE detects mismatched authenticated request/order identity and holds the write.
4. Attribution & impact
Evidence points to the Supervisor handoff; its order artifact and dependent lookup, policy, decision are suspect.
5. Recovery & oracle
Restore ORDER-A, redo dependent lookups and policy check, re-obtain applicable consent, then simulate one correct action and verify database state.
A successful result means the originally requested order was changed only when eligible and authorized, the incorrect order was untouched, and the user-facing response matches the final simulated state.

7.3  Independent ground truth
For each scenario, persist (a) task ID, initial database and policy snapshot, (b) expected required/forbidden tool actions and final-state assertions, (c) fault injection location and mechanism, (d) separately adjudicated decisive causal step(s), (e) permitted recovery and side-effect limits, and (f) exact validation logic. These labels live outside the diagnostic prompt. The injected step is not automatically the ground-truth root cause; replay or counterfactual tests should establish whether a fault materially changed the outcome.
Proposed study scale: start with the published 114 retail benchmark tasks where practical, then construct approximately 40–60 reproducible fault cases plus clean controls. This is an implementation target, not a claim that the full suite or labels already exist. A fault that produces no observable task failure must not count in the recovery-success denominator.

9  Research questions
RQ1: Can cross-agent dependencies improve localization of a failure’s decisive agent and step compared with flat traces or within-agent-only diagnosis?
RQ2: Can a dependency-aware safety gate reduce unsafe simulated state changes while keeping false blocking acceptably low?
RQ3: Can selective recovery reduce repeated work without lowering independently verified task completion compared with full retry?
RQ4: Does independent environment verification reduce mistakenly accepted repairs?

11  Limitations and research honesty
The design assumes instrumentation access to agent messages, handoffs, tools, and state versions. Some data dependencies may be missing; uncertain state will be treated conservatively. LangGraph checkpoint rollback does not reverse simulator side effects; write-once operation controls and independent verification are essential. LLM-based diagnosis is probabilistic, and an anomaly score is not proof of causation. Learned HGT detection requires training data beyond a minimal retail prototype. No production payments, refunds, or customer data operations will be used.
The supplied anonymous AgentTether source mirror is referenced as an implementation resource, but its file-level README/source contents were not retrievable in this review environment. Consequently this proposal is grounded in the accessible AgentTether paper and verified τ-bench policy/repository; it does not claim a completed source-level audit, copied package structure, or guaranteed plug-and-play integration.
12  Expected deliverables
An operational LangGraph retail MAS; a structured trace and cross-agent dependency graph; a fault-injection scenario library; an evidence-based attribution and containment controller; a bounded recovery and verification loop; a visual trace-to-repair demonstration; and an empirical comparison showing both successes and failures against the defined baselines.
